# First-deal entry contract

**Status:** design for implementation and independent auth/record review; no new behavior is deployed by this document. The target is one real deal, with human oversight and individually revocable agent credentials. Existing account sessions, guest invitation and acceptance are described separately from proposed delegation.

## Principals and proof

- **Owner human:** signs up or signs in through the existing verified-email account flow and CAPTCHA. A validated non-anonymous session identifies an account, not a legal person. That account owns the deal.
- **Owner AI:** holds only a secret delegation issued by the owner account. The service proves possession and verifies the live grant; an owner-chosen label is not independent agent identity or proof of intent.
- **Counterpart human:** signs up or signs in to their own verified-email account and explicitly grants their AI authority. For this entry path, the service binds that account to the intended recipient by requiring its currently verified email to match the owner's invited address, and possession of the deal's single-use invitation. This establishes an account-and-invite relationship, not a legal identity. Normalize using one specified, tested rule; missing, unverified, changed or nonmatching email fails closed. Do not let a typed address or a forwarded invite alone establish the account binding.
- **Counterpart AI:** presents the invite and its counterpart-account delegation for acceptance, then its scoped delegation for that deal. It proves possession, not an independently verified agent identity.
- **Human guest:** may use the existing single-use invite to accept and its resulting guest capability for that deal. This is bearer authority and its claimed email remains unverified; it is not counterpart-account delegation.

## Create, grant, act, revoke

1. **Create.** Add one server-side create endpoint for the verified owner account session. It validates the same fields and ownership as today's client insert, creates the draft and invite, and returns the deal ID and invitation. Owner human creates the draft for this first path; no agent create permission or account-wide delegation. During migration old client inserts remain as currently authorized until clients are switched; their existence must not be mistaken for delegated create. Creation stores the deal row; it does not claim to append a creation event. Record only what actually occurs.
2. **Grant.** On an existing deal, the respective authenticated human issues a separate per-deal credential. The owner issues `issuer_kind: owner_account`; the counterpart issues `issuer_kind: counterpart_account` only after the verified-account plus invite binding above. Owner cannot issue a counterpart grant; a guest bearer cannot issue either grant. A grant stores immutable nonsecret ID, issuer account ID/kind, deal ID, operation scopes, issuance and expiry and revocation state; store only a secret verifier, return the high-entropy secret once, never record it in events or logs. The issuer may list and revoke its grants. Define a finite expiry at issue; refuse expired grants. Account recovery uses the ordinary human sign-in flow.
3. **Scope.** `read` permits only this deal's authorized projection and receipt; `accept` permits only counterpart acceptance; each allowed event type is an explicit permission, further constrained by the deal's performer/receiver role and state. No wildcard, no grant-management or create permission. Approval/acceptance is explicitly granted, never implied by read or ordinary write. An absent or broader-than-allowed scope fails closed. Before any delegated read, accept, append or replay the server validates the secret, issuer kind/account, exact deal, operation, expiry and revocation; it never treats a delegation as an owner JWT or a direct RLS bypass.
4. **Accept.** Human guest follows the existing invite-bearer path. For AI2AI, the counterpart AI supplies both the invite and its `counterpart_account` grant. Under one transaction and consistent lock order (contract, then delegation), revalidate the live delegation, account/invite binding, scope, invite single-use/expiry and shown terms; consume the invite, persist the accepted snapshot and append the acceptance event together. Derive issuer kind and identity from the stored grant and verified session, never request-body claims. A revoked/expired grant or changed terms admits no acceptance. Keep the human-guest path visibly bearer-based; never fall back from a failed delegated request to it.
5. **Record and read.** For each new delegated event, persist the nonsecret grant ID, issuer kind and bounded authority context with the event, and bind it into the event's canonical payload/hash under an explicitly versioned, reviewed format. Preserve existing rows and their hash versions unchanged; historical writer remains unknown. Acceptance records the actual accepted snapshot and the presented authority basis. Invite handoff, negotiations and real-world performance are not automatically observed. Service assertions are not independent proof of identity, intent, truth or time. Readers report checks and truncation honestly; they do not infer author from hash version.
6. **Revoke and retry.** Only the issuing human account can revoke its agent grant, including the counterpart's. Authorization and revocation use a common lock/transaction boundary: after revoke commits, no new delegated write or read is admitted. An already admitted operation may complete before revoke; an in-flight keyed replay may return only the same delegation's own earlier event under the documented exception in `Decisions.md:44`. For a fresh replay, recheck live grant and scope before lookup; bind idempotency to deal, type, actor and delegation, and refuse conflicts and cross-grant disclosure. Never re-admit an expired grant while it waited for the lock. Reads already returned cannot be recalled.
7. **Guest recovery.** `reissue-guest-access` remains callable only by the authenticated owner human account, not by either agent delegation or the guest. It rotates the existing human-guest bearer with its existing commit boundary. It does not issue or revoke counterpart-account delegations; the counterpart human revokes those independently. A lost grant secret is replaced by a new grant after the issuer revokes the old one.

## Minimum proof before entry goes live

Cross-review auth and record changes independently. Test correct and wrong issuer/deal/role/scope; unverified or mismatched account email; stolen/forwarded invite; missing/expired/revoked grant; no fallback; double accept and changed terms; revoke racing read/write/accept and expiry while waiting; retries and cross-grant key collisions; exact accepted snapshot and hash recomputation on legacy and new events. Test both human-guest and AI2AI paths against the authorized E2E project before a separately authorized release. Read and write checks must fail closed on lookup failure. The current guest API's v1 `server_attested` label is only a format label, not writer proof; use the separately planned safe API migration or a truthful client interpretation before external agent use.

## Out of scope for the entry path

Cross-contract or account-wide agent credentials, agent-created deals, agent-managed grants or guest reissue, guest-bearer-derived delegation, negotiation history/engine, creation event, identity verification beyond account/invite binding, external timestamps/checkpoints, scores, payment execution, UI polish and broad refactoring. These may be added later without claiming they already exist. Operator and service-role holders remain inside the trust boundary; no independent time or resistance to privileged rewrite is promised.
