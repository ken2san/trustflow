# Row 5 — Delegated Owner Read Implementation Plan

> Kenji confirmed the Row 5 decisions on 2026-11-24. Claude builds and Codex reviews. Update the schedule's owner cell to “Claude builds / Codex reviews” when Row 5 starts.

**Goal.** A live owner-issued `read` grant can retrieve an authorized projection and portable receipt for one deal, with a transaction boundary shared with revocation. The guest projection and download carry v5 canonical inputs without broadening guest access.

**Architecture.** An independent, default-off Edge route uses Row 4's grant admission and a single service-role RPC to authorize and materialize a bounded snapshot. The guest keeps its existing bearer route and response versions. C3 is an effective-policy check, with a migration only if a separate, confirmed policy defect requires one.

**Stack and spec.** Supabase Edge Functions, PostgreSQL, existing v5 canonical/verifier modules, Vitest and Playwright. Read [entry contract](../entry-contract.md) §§1–7, [minimum usable design](../minimum-usable-design.md) C1–C3, [schedule](../schedule.md) row 5, and [row 4](row4-owner-append.md) §§4a–4c. Depends on rows 1, 3 and 4.

## Scope and completion

- One deal and an explicitly granted `read` scope. Owner JWT, guest access token, invite and counterpart delegation retain their existing paths. Counterpart delegated read is row 12. No owner-session fallback, grant management, acceptance, guest rotation, event insertion or payment execution in this route.
- No migration of historical events, hash or receipt format change, default guest response-version flip, or change to legacy `provenance` wording. Existing receipt and guest-export formats are distinct. A complete canonical block supports offline event-hash recomputation; a projected payload cannot reproduce the full payload digest.
- Done when local tests prove authority and both revoke orders, a v5 row built by the real writer survives guest projection → download → offline canonical verification, and C3 policy and behavioral coverage is recorded on the authorized target. Record implementation review and separate E2E evidence. Production release has its own authorization.

## 5a. SQL admission, snapshot and revocation

**Existing boundary.** `20261118214020_entry_agent_credentials.sql` holds immutable grant evidence and revokes via contract `FOR UPDATE` → grant `FOR UPDATE`. `20261124120000_entry_agent_resolver.sql` checks owner binding, live grant and scopes for the six write types. It refuses `read` even with `p_for_insert = false`. `20261124130000_delegated_owner_append.sql` contains the pre-lock `private.v5_grant_precheck`, and its append/replay entry points have service-role-only EXECUTE.

**Migration required.** Add a new forward migration after Row 4's deployed migration sequence, with a proposed suffix `_delegated_owner_read.sql`. Confirm sequence and use the project's migration creation workflow at implementation. Add `public.read_delegated_owner_deal(p_contract_id uuid, p_credential_id uuid, p_secret_hash text) returns jsonb`. There is no new table, grant scope, event field, or RLS access path. Prefer a narrow read branch in private shared authorization with an explicit operation mode. Preserve the existing resolver signature as the append/replay wrapper and keep that wrapper's six-operation allowlist. The read entry point hardcodes `read`; no client-controlled type, issuer, grant-mode or role parameter. Reuse `private.v5_grant_precheck`. A read-specific helper is acceptable if it avoids disturbing already-deployed writer behavior and has explicit parity tests for common checks.

| Step | Contract |
|---|---|
| 1. Before a deal row lock | Require READ COMMITTED using `public.require_read_committed`. Validate grant possession and deal match through the existing private non-row-locking precheck. Wrong deal, missing grant and wrong hash follow one public refusal. No deal projection, event count or receipt lookup precedes authorization. |
| 2. Lock | Take the contract row lock first, then the matching grant `FOR SHARE`, in the same sequence as row 4. Start with contract `FOR UPDATE` to reuse the tested serialization with revoke and writes. Lock lifetime is the RPC transaction. |
| 3. Decide live authority | Sample `clock_timestamp()` once after both locks. Verify exact deal and hash, `owner_account`, issuer equal to locked `earner_user_id`, `revoked_at IS NULL`, `expires_at > sample`, and exact `read` scope. Use the same checks on draft and accepted deals. Read has no performer/receiver restriction and does no gate lookup. |
| 4. Materialize | After authorization, select an explicit contract projection and ordered event slice under the locks. Collect rows, total count and tail marker from one snapshot (prefer one SQL statement for count and slice). Read the first acceptance anchor in the same materialization. No separate Edge DB read for acceptance, event count or receipt. Limit to a 500-event, byte-limited prefix. Start with a 1 MiB budget for the materialized event slice and verify the response size after receipt shaping. Cut at a row boundary and keep the exact total and truncated marker. |
| 5. Hand off | Commit with the authorized materialized data. Edge may shape the already-materialized response after commit without further database reads. Each new call, including retry, rechecks the live grant. No reusable authorization result, cache token, offset or cursor in the initial interface. |

**Boundary against revoke.** If revoke commits first, read refuses, including a read queued behind the contract or grant lock. If read wins, revoke waits until the authorized data is materialized and the read transaction ends. Its HTTP response may reach the caller after revoke commits because it contains only data admitted in that transaction. A fresh read after revoke cannot get a slice, count, receipt or cached data. A grant that expires while waiting fails on the post-lock sample. Expiry uses the admission sample; a response to an already admitted read can finish serializing. This route has no keyed replay exception. PostgreSQL READ COMMITTED can use a fresh snapshot per statement; keep count and page in one statement and preserve the locks across authorization and materialization. [PostgreSQL transaction isolation](https://www.postgresql.org/docs/18/transaction-iso.html#XACT-READ-COMMITTED) · [Row locks](https://www.postgresql.org/docs/18/explicit-locking.html#LOCKING-ROWS)

**ACL.** Service-role-only RPC with `SECURITY DEFINER`, qualified references and empty `search_path`. Revoke default EXECUTE from PUBLIC, `anon` and `authenticated` in the migration. Private helpers stay outside exposed schemas and are inaccessible directly to those roles and to `service_role`. Verify effective privileges in the migration and fixture, including inherited grants. Reuse the exact-signature inventory rules in `tests/sql/entry_agent_credentials_inventory.sql` if a new private helper names the credential table. The Edge role is trusted to call this RPC, and the RPC still requires the presented grant verifier to return any deal data.

**SQL tests.** Add `tests/sql/delegated_owner_read.sh` and `tests/sql/delegated_owner_read_races.sh` following the disposable runners. Prove wrong deal, swapped grant, wrong secret, wrong issuer/kind, missing `read`, revoked, expired, owner change, closed/missing v5 gate independence, non-READ-COMMITTED rejection and direct RPC/helper ACLs. Keep closed/missing gate fixtures disposable. Assert failed authorization returns no projected fields, count or receipt material. Use two actual sessions and observed blockers to pin read-first and revoke-first, fresh read after revoke, expiry while waiting, and a failed possession check that returns while the contract is locked. Assert deterministic `(created_at, id)` ordering and cap/count from a single materialization. Re-run the existing resolver and append/race suites when touching shared logic; pin that `read` cannot enter append/replay.

## 5b. Edge transport and owner projection

**Approved interface.** New `supabase/functions/delegated-owner-read/index.ts`, `POST` with JSON `{ "contract_id": "<uuid>" }`, existing public anon bearer for gateway transport (superseded 2026-11-25, T258: the publishable key in `apikey` and no `Authorization`; see `row5-5b-e2e-enable.md`), and `x-trustflow-grant` for actual authority. Reuse `_shared/delegatedAuth.ts` and `_shared/cors.ts`. Preserve the pinned gateway behavior and reject mixed guest/session credentials. Hash the header secret in Edge and send only the digest to SQL. Keep `ENTRY_DELEGATED_READ` default off and independent of the append rollout. Apply and confirm the RPC before deploying, and return 503 without a fallback if the RPC is unavailable. Verify preflight for allowed and disallowed origins. The Row 5 E2E deploy waits for Row 4's gateway, CORS and platform-log proofs.

| Result | Wire behavior |
|---|---|
| 200 | One JSON envelope with `contract`, `events`, `read_boundary` and `receipt`. Explicit `Cache-Control: private, no-store`; no redirects or authenticated content in URL, caches or logs. |
| 400 / 405 | Malformed deal-independent body or unsupported method. OPTIONS is the existing CORS pattern. |
| 403 | `delegation_refused` for wrong/missing deal or grant, malformed/mixed credentials, revoked/expired grant, wrong issuer/owner or scope. Return no lookup details. |
| 503 / 500 | Default off or missing RPC gives `delegated_read_unavailable`; unexpected failure gives a generic 500, no raw exception. Structured logs carry a fixed reason and validated IDs or null only. |

**Approved data boundary.** Contract fields are `id`, `state`, `project_name`, `dod`, `amount_minor`, `currency`, `deadline`, `performed_by`, and the display-name field needed to reproduce the existing current snapshot. Include legacy amount only as needed for snapshot parity. Include only allowlisted event statement fields, recorded assurance label where applicable, `event_hash` and stored canonical values. Leave contact addresses, invite and guest-access material, grant verifiers, internal notes, idempotency keys and unrelated account data out of the wire envelope. No table-wide `select *` in an exposed response. Grant ID and issuer kind may appear where they are recorded v5 canonical inputs; they identify the recorded grant authority.

**Receipt.** Use the same format as `scripts/lib/receiptV2.mjs` and `docs/v5-receipt-format.md`. Extract or reuse its pure shaping rules through a Deno-compatible shared helper if needed, leaving the owner-session CLI's authenticated paging entry point and existing format compatible. Build receipt metadata from the materialized rows only. Emit canonical inputs, event hash, read completeness, and the current snapshot with a separate digest. Include accepted terms in the receipt only when its acts include the verified acceptance anchor used by the offline verifier. Report an anchor outside the prefix as unavailable for that receipt. The receipt need not include raw payloads, idempotency keys or legacy authentication details outside the approved projection. An empty trail gets `receipt: null` with a separate read-boundary result because the verifier requires acts. For a partial trail set v2 receipt `read.start = 'first_event'` and `read.tail_complete = false`, with `recorded_count` and the truncated marker on the enclosing response. Prove that the offline verifier checks the available prefix and reports the boundary. Full pagination is deferred to a later row, where it will require stable ordering, a bound high-water mark and per-page reauthorization.

**Edge tests.** Add `tests/unit/delegatedOwnerRead.test.js`. Cover flag off, absent/mixed/malformed credentials, no deal pre-read, no fallback, hash-only RPC parameters, application logs with a noncredential canary, RPC absence, generic thrown failure, no-store headers, and withheld fields in both projection and receipt. Cover draft and accepted evidence, legacy/v5 mixes, empty and capped trails, and absent accepted evidence even when the contract state suggests acceptance. Add `tests/e2e/delegated-owner-read.spec.js` for the approved fixture and real gateway, including a returned receipt accepted offline and a newly refused read after revocation. Run the gateway log check with a noncredential canary first. Use a separately authorized disposable grant for the credential check and revoke it afterward. Stop rollout if the platform captures the credential.

## 5d. C3 effective-policy check

**Source baseline.** `20261011212432_restrict_events_to_verified_owner.sql` replaced the historic email predicate on `public.events` with a contract-owner `auth.uid()` check. Contract read policies must be inventoried separately, including the account-ID party predicate in `20260921000000_contracts_role_rename.sql`. Neither `hirer_email` (a self-claim) nor `invited_hirer_email` (the invite target) grants direct access. The Row 1 issuance RPC matches confirmed `auth.users.email` against `invited_hirer_email` using `lower(btrim(...))`, with the existing invite and distinct-account conditions. The owner read RPC uses the bound account ID and grant, without email authority. C3's verified-email assumption depends on confirmation being required (`Decisions.md`, 2026-11-19).

- Add `tests/sql/delegated_read_rls.sql`, or extend the existing read-only catalog inventory if it can assert the same behavior. Inspect effective `pg_policies`, grants and applicable views/RPCs for `contracts` and `events` under `anon`, `authenticated` and `service_role`. Positive direct-RLS control for the owner. Negative controls for authenticated unrelated users, matching self-claimed `hirer_email`, JWT/email claim matches with case/space differences, and unverified accounts. Also test the legitimate guest via its bearer endpoint, not direct RLS. Verify normalized matching on the existing confirmed-email plus invite issuance path and refusal on mismatched/unverified email or absent invite. Use fabricated local fixtures; a service-confirmed bot is not proof of the real email-confirmation path.
- No C3 migration is expected if source and effective policy match. If an observed policy authorizes via self-claimed email, record the exact target and policy and bring a narrowly scoped correction for review. Never normalize this branch into broader access.
